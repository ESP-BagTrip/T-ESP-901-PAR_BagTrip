# i18n

> Derniere mise a jour : 2026-05-23

## Vue d'ensemble

BagTrip est bilingue EN / FR de bout en bout. La langue n'est pas une couche cosmetique
posee au-dessus de l'UI : elle est threadee depuis le device jusqu'aux prompts LLM
backend en passant par les messages d'erreur, les notifications push et les emails
de partage. Aucun fragment FR ou EN n'est hardcode dans le code Dart : tout passe
par `AppLocalizations.of(context)!.<key>` et est resolu via les fichiers ARB.

Principes non-negociables :

- Toute chaine visible utilisateur passe par ARB. Zero litteral FR / EN dans le code.
- Toute cle ajoutee existe dans `app_en.arb` ET `app_fr.arb` dans le meme commit.
- Les compteurs utilisent un plural ICU, jamais un `if (count == 1) ...` en Dart.
- Les messages d'erreur passent par `toUserFriendlyMessage(error, l10n)`.
- Le `locale` actif est envoye au backend sur chaque call AI / notif / partage
  qui peut produire du texte cote serveur.

## ARB files

Les deux fichiers sources :

- `bagtrip/lib/l10n/app_en.arb` (en, locale fallback)
- `bagtrip/lib/l10n/app_fr.arb` (fr, template selon `l10n.yaml`)

Aujourd'hui environ 1800 lignes par fichier, strictement synchrones cle pour cle.
Une cle presente dans un seul des deux fichiers est un bug : la generation echoue
ou pire le run renvoie la cle brute a l'ecran.

### Cles simples

```json
{
  "searchFlightButton": "Search Flight",
  "passengersTitle": "Passengers"
}
```

Cote Dart : `l10n.searchFlightButton`.

### Placeholders typees

Chaque variable de la chaine doit etre declaree dans le bloc `@<key>` avec un
type explicite (`String`, `int`, `double`, `DateTime`, `num`). Sans declaration,
le generateur produit un parametre `Object` impossible a typer cote appelant.

```json
{
  "multiDestFlightTitle": "Flight {index}",
  "@multiDestFlightTitle": {
    "placeholders": {
      "index": { "type": "int" }
    }
  },

  "tripShareInvitedOnDate": "Invited on {date}",
  "@tripShareInvitedOnDate": {
    "placeholders": {
      "date": { "type": "String", "example": "05/12/2024" }
    }
  },

  "ticketEmissionDeadline": "Ticket emission before {date}",
  "@ticketEmissionDeadline": {
    "placeholders": {
      "date": { "type": "String" }
    }
  }
}
```

Cote Dart :

```dart
l10n.multiDestFlightTitle(2);
l10n.tripShareInvitedOnDate('05/12/2024');
```

Les dates affichees sont formatees en amont avec `intl` (locale courante) puis
passees en `String` au placeholder : on garde le formatage au point d'appel et
le placeholder reste dumb.

### Plurals ICU

Tout ce qui se decline avec un compteur utilise la syntaxe ICU `plural` avec
les categories `=0`, `=1`, `other`. C'est imperatif : FR et EN n'ont pas les
memes regles (FR : 0 est singulier ; EN : 0 est pluriel), un `if` Dart casse
silencieusement la langue qu'on n'a pas testee.

EN :

```json
{
  "stopsLabel": "{count, plural, =0{Direct flight} =1{1 stop} other{{count} stops}}",
  "@stopsLabel": {
    "placeholders": { "count": { "type": "int" } }
  },

  "tripDurationDays": "{count, plural, =1{1 day} other{{count} days}}",
  "@tripDurationDays": {
    "placeholders": { "count": { "type": "int" } }
  },

  "baggageQuantity": "{quantity, plural, =1{1 bag} other{{quantity} bags}}"
}
```

FR :

```json
"stopsLabel": "{count, plural, =0{Vol direct} =1{1 escale} other{{count} escales}}",
"tripDurationDays": "{count, plural, =1{1 jour} other{{count} jours}}",
"baggageQuantity": "{quantity, plural, =1{1 bagage} other{{quantity} bagages}}"
```

Cote Dart : `l10n.stopsLabel(0)`, `l10n.tripDurationDays(7)`.

## Generation

Pipeline standard Flutter `gen-l10n`, configuration dans `bagtrip/l10n.yaml` :

```yaml
arb-dir: lib/l10n
template-arb-file: app_fr.arb
output-localization-file: app_localizations.dart
```

`pubspec.yaml` active la generation au pub get via :

```yaml
flutter:
  generate: true
```

Les fichiers generes (`app_localizations.dart`, `app_localizations_en.dart`,
`app_localizations_fr.dart`) vivent dans `bagtrip/lib/l10n/` et sont commit
dans le repo (Flutter les regenere automatiquement au `flutter pub get`).

Workflow :

```bash
cd bagtrip
flutter pub get
# ou apres edition d'un ARB, force la regeneration :
flutter gen-l10n
```

Si une cle est utilisee dans le code mais absente d'un ARB, `flutter analyze`
echoue. Le pre-commit hook (`make check`) execute `flutter analyze` et bloque
le commit.

## Utilisation dans le code

Recuperation du bundle dans n'importe quel widget :

```dart
final l10n = AppLocalizations.of(context)!;
return Text(l10n.searchFlightButton);
```

Le `!` est intentionnel : `AppLocalizations` est garanti present sous
`MaterialApp.localizationsDelegates`. Un null ici signale un bug d'init
(tree sans `MaterialApp` parent), pas un cas a gerer.

Setup app-level dans `main.dart` :

```dart
MaterialApp.router(
  localizationsDelegates: AppLocalizations.localizationsDelegates,
  supportedLocales: AppLocalizations.supportedLocales, // [en, fr]
  // ...
);
```

`AppLocalizations.localizationsDelegates` est deja la liste complete
(`delegate` + Material + Cupertino + Widgets), pas besoin de la composer
a la main.

Lecture du locale actif dans un widget (utile pour formater une date `intl`
ou envoyer une requete backend) :

```dart
final locale = Localizations.localeOf(context).languageCode; // 'en' | 'fr'
```

Hors `BuildContext` (jobs en arriere-plan, FCM token refresh, AuthBloc au boot) :

```dart
final locale = PlatformDispatcher.instance.locale.languageCode;
```

## Messages d'erreur

`bagtrip/lib/utils/error_display.dart` fournit `toUserFriendlyMessage(error, l10n)`,
le seul point d'entree autorise pour afficher une erreur. Toute UI qui catch un
`Failure(error)` doit passer par ce helper :

```dart
ScaffoldMessenger.of(context).showSnackBar(
  SnackBar(content: Text(toUserFriendlyMessage(error, l10n))),
);
```

La resolution est en deux niveaux :

1. **Code backend explicite** (`AppError.code`) : table de mapping
   (`ALREADY_PREMIUM`, `REFUND_AMOUNT_EXCEEDS_REMAINING`, `STRIPE_CUSTOMER_MISSING`,
   etc.) vers une cle ARB precise (`l10n.errorAlreadyPremium`, ...).
2. **Type AppError** : fallback large par type (`NetworkError` -> `l10n.errorNetwork`,
   `ValidationError` -> `l10n.errorValidation`, `RateLimitError` -> `l10n.errorRateLimit`,
   `QuotaExceededError` -> `l10n.errorQuota`, etc.).

`ValidationError.message` n'est jamais affiche brut : le backend renvoie ses
messages en EN, les exposer leak l'anglais dans une UI FR.

Pour ajouter un nouveau code metier :

1. Ajouter la cle `errorXxx` dans `app_en.arb` ET `app_fr.arb`.
2. Ajouter la branche dans `_codeToMessage` de `error_display.dart`.
3. Couvrir avec un test dans `test/utils/error_display_test.dart`.

## Locale threading backend

Le `locale` actif du client est envoye au backend chaque fois que le serveur
peut produire du texte visible utilisateur. Cote app, on lit le locale via
`Localizations.localeOf(context).languageCode` (UI) ou
`PlatformDispatcher.instance.locale.languageCode` (hors widget tree, ex :
`AuthBloc`, FCM `onTokenRefresh`).

Points d'envoi recenses :

- `AiRepository.planTripStream(..., locale: ...)` et `proposeDestinations(..., locale: ...)`
  pour le wizard plan trip (`PlanTripBloc` propage `event.locale` jusqu'au stream SSE).
- `NotificationRepository.registerDeviceToken(token, platform, locale: ...)` au
  cold start et a chaque `onTokenRefresh` Firebase, pour que les push FCM soient
  composees dans la bonne langue cote backend.
- `AuthBloc` au register / refresh : envoie le locale pour les emails transactionnels.
- `bookingRepository.refund(..., locale: ...)` pour le wording du recu Stripe.

Cote backend (`api/`), le contrat est documente dans `CLAUDE.md` :
`PlanTripRequest.locale` -> `TripPlanState.locale` -> chaque node LangGraph
appelle `render(prompt_name, locale=state.get("locale", "en"))`. Les templates
Jinja2 vivent dans `src/agent/prompts/templates/{en,fr}/*.j2`. Le fallback FR -> EN
est automatique via `{% include "en/..." %}` tant que la traduction FR n'est
pas ecrite. Les notifications push localisees suivent la meme regle :
le backend choisit la langue a partir du `locale` enregistre sur le device token.

Cle pratique : si tu ajoutes un nouvel endpoint qui genere du texte cote
serveur (LLM, email, notification, PDF), passe le locale en parametre des
le premier commit. Le rajouter plus tard implique de toucher schema Pydantic,
tests, client Flutter et templates en meme temps.

## Ce qu'il manque

- **Audit exhaustif des hardcoded strings** : un `grep` cible sur `Text\('[A-Z]`
  remonte encore quelques cas residuels dans des dialogs debug et des empty
  states tardifs. A planifier en passe systematique.
- **Tests de coverage l10n** : pas de test qui asserte la parite EN / FR
  (toutes les cles d'un fichier presentes dans l'autre). Un script de check
  au pre-commit eviterait les regressions silencieuses.
- **Traductions FR backend incompletes** : plusieurs templates `src/agent/prompts/templates/fr/`
  sont encore des `{% include "en/..." %}`. A finir au fil des sprints prompts.
- **Pluriels FR atypiques** : le cas "1.5 jours" / "0,5 jour" (decimaux) n'est
  pas couvert par ICU `plural` actuel (toujours `int`). A trancher si le besoin
  produit remonte.
- **Langues supplementaires** : architecture prete (il suffit d'ajouter
  `app_es.arb` et `Locale('es')` dans `supportedLocales`), mais ES / DE / IT
  ne sont pas sur la roadmap actuelle.
- **Formats date / nombre** : le formatage passe par `intl` au point d'appel,
  pas centralise. Une extension `DateTimeExt.localizedShort(locale)` reduirait
  la duplication.
